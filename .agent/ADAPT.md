# ADAPT — キットを別のプロジェクト用に組み替える手順

「このキットを○○用に書き換えて」と言われたら、この手順に従う。
このキットの**骨格（ループの3条件・書き込み権限・Checker・状態のファイル化・仮説台帳と探索モード・Reviewer）は残し、名前と中身を題材に合わせる**のが目的。

**組み替えで一番大事な原則：評価に関わるもの（完了条件・目標値・評価方法・仮説の型）は、エージェントが案を出し、人間が決める。**
これからループを回すエージェント自身が合格基準を決めると、自分で自分を承認するのと同じになるため。

## ステップ1：聞き取り（まとめて1回で聞く）

次を確認する。ユーザーの依頼文から分かるものは聞かずに埋め、推測した内容は「こう解釈しました」と示す。
資料はユーザーの要約ではなく、原文（ファイル）を受け取る。

1. **入力の資料は何か**（論文、仕様書、競技のルール、既存コードの移植元、ベンチマークの定義……）
2. **「完了」を何で判定するか**
   * 性質のテストで判定できる（関数の性質、仕様の条件）
   * 数値の目標で判定する（精度、速度、スコア）
   * 両方
   * **まだ分からない**（改良・最適化など、目標値を事前に決められない）→ ステップ2の「2段階の計画」を作る
3. **言語とテストの実行方法**（既定は Python の unittest）
4. **重い実行（実験）があるか**。あるなら1回にかかる時間とお金の目安
5. **評価のぶれ**：乱数を使うか。同じ条件で何回まで回せるか（seed の数・予算を決める材料）
6. **うまくいかない時に疑う場所の心当たり**（任意。あれば仮説の型の案に反映する）
7. **サンプル（example_es）を残すか消すか**（既定：消す）

## ステップ2：対応表を作って見せる

キットの概念を、そのプロジェクトの言葉に置き換えた表を作り、ユーザーに見せて合意を取る。例：

| キットの概念 | 既定の名前 | このプロジェクトでは |
| --- | --- | --- |
| 入力の資料 | `papers/<名前>/paper.md` | 例：`specs/<名前>/spec.md` |
| 検証できる主張 | `claims.md` | 例：受け入れ条件 |
| 数値の目標 | `targets.json` | 例：性能要件 |
| 外部に依存しない層 | `core/` | 例：`domain/` |
| 実験 | `experiments/` → `runs/` | 例：ベンチマーク |

**名前を変えるのは、意味がずれる時だけ。** 変えなくて済むなら変えない方が、このキットの説明と照らし合わせやすい。

対応表と一緒に、次の4つを**案として**見せる。どれもエージェントは決めない。ユーザーの合意（または修正）を受けてからステップ3に進む。

### 2-1. 評価方法と、その抜け道

* 完了をどう測るかの案（どの指標を、何回の実行の何で集計するか）
* **その評価では高得点だが、実は進歩していない抜け道を最低2つ**と、それぞれの塞ぎ方
  （例：テストデータに過剰に合わせる・評価の対象外の場所で手を抜く・乱数の当たり外れ・指標の定義の穴）
* 塞げない抜け道は、塞げないと正直に書き、Reviewer と人間が見張る点として `guardrails.md` に足す案を出す

### 2-2. 仮説の型（`explore.hypothesis_types`）

この題材で「うまくいかない時に疑う場所」の分類を、**5〜8個**提案する。形式は次のとおり。

| 型 | 何を疑うか | 代表的な仮説の例 |
| --- | --- | --- |
| （例：未確定点の解釈） | 資料に書かれていない選択 | 定数 c の値が論文と違う |

* 型どうしが重ならないようにする。ある仮説がどの型か迷うなら、分け方が悪い
* 細かすぎる型（例：パラメータ1つごと）は、言い換えれば排除をすり抜けられるので作らない
* 粗すぎる型（例：「実装」1つだけ）は、正当な深掘りまで止めてしまうので作らない
* 「資料・評価そのものの誤り」に当たる型を1つ入れる（そこに行き着いたら人間に戻す合図になる）

### 2-3. 数値の設定と根拠

`budget`・`explore`（`stagnation_window`・`min_rel_improvement`・`max_failed_predictions_per_type`）・`stats`（`min_seeds`・`ci`）の値を、
ステップ1の4（コスト）と5（ぶれ）から根拠を付けて提案する。例：

* 1回が重いのに `stagnation_window` が大きいと、探索モードに入る前に予算が尽きる。`max_runs_per_claim` は `stagnation_window` の3倍以上を目安にする
* 乱数を使わない題材なら `min_seeds` は 1。使うなら、ぶれの大きさから判定不能が出すぎない数にする

### 2-4. 2段階の計画（「完了」がまだ分からない場合だけ）

目標値を決めずに外側のループを回すと、何が進歩か分からないまま微調整が続く。そこで段階を分ける。

1. **第1段階（調べる）**：目標値は決めない。ベースラインと、効いていそうなパラメータの**診断実験**（`kind: diagnostic`）の案を出す。
   診断実験は目標値が無くても回せる。既定値を `sweep` の値に含めれば、ベースラインも同時に測れる
2. **人間が決める**：診断の結果を見て、人間が目標値（例：ベースラインから X% 改善）を `targets.json` に書き、`lock.py` で承認する
3. **第2段階（当てにいく）**：ここから通常の外側のループ（試行・探索モード）を回す

この場合 `progress.md` の「次の一手」には、第1段階の診断実験の一覧と「結果が出たら人間が目標値を決める」を書いておく。

## ステップ3：組み替える

合意が取れたら、次の順で変更する。数値・型・評価方法は、**ステップ2で合意したものをそのまま**使う（組み替え中に勝手に変えない）。この作業中に限り、`scripts/`・`lab.config.json`・`.claude/`・`.agent/goal.md` を編集してよい。

**Claude Code で作業している場合**、これらの場所はフック（`scripts/hooks/guard.py`）が書き込みを拒否する。
変更を始める前に、ユーザーに `python scripts/adapt_mode.py on` の実行を依頼して待つ（自分では実行できない）。
Hermes など他のエージェントでは不要。

1. `lab.config.json`
   * `project_name`、`dirs`（フォルダ名を変えたなら実際のフォルダも移動する）
   * `check_commands`（言語に合わせる。例：`["npm", "test"]`、`["cargo", "test"]`、`["pytest", "-q"]`）
   * `pure_layer`（層の名前と、その層で禁止する import。Python 以外なら下記の注意を参照）
   * `budget`（実験が重いなら回数を減らす。`max_diagnostic_runs_per_claim` は診断実験の上限）
   * `explore.hypothesis_types`（仮説の型の一覧。題材で疑う場所の分類に合わせる。細かすぎると排除が効かず、粗すぎると方向転換を強制しすぎる）
   * `explore` の停滞の判定（`stagnation_window`・`min_rel_improvement`・`max_failed_predictions_per_type`）
   * `stats`（`min_seeds`・信頼区間。乱数を使わない題材なら `min_seeds` を 1 にする）
2. `.agent/templates/` の雛形の言葉を題材に合わせる
3. `AGENTS.md` の部屋の地図と合言葉の表を、新しい名前に合わせる（**構造と規則の数は減らさない**）
4. `.agent/goal.md` をこのプロジェクトの目的で書き直す（書いた後、ユーザーに確認してもらう）
5. `.agent/guardrails.md` に題材固有の禁止事項と、2-1 で塞げなかった抜け道があれば足す
6. サンプルを消す場合：`papers/example_es/`・`src/example_es/`・`tests/example_es/`・`experiments/example_es/` を削除し、
   `.agent/locks.json` から `example_es` の項目を消し、`runs/` の中身と `runs/INDEX.jsonl` を空にする
   （削除の前に、消すものの一覧をユーザーに見せて確認を取る）
7. git が無ければ `git init` して、組み替えた状態を最初のコミットにする

### Python 以外の言語にする場合

* `scripts/` は Python のまま使ってよい（言語に依存するのは `check_commands` と `pure_layer` だけ）
* `check.py` の依存方向の検査は Python の import しか読めない。その言語の仕組み
  （例：ESLint の `no-restricted-imports`、Rust のモジュール公開範囲）に置き換え、`check_commands` に追加する。
  置き換えたら `lab.config.json` の `pure_layer.dir_name` を存在しない名前にして、Python 用の検査を無効にする
* `scripts/run.py` の `entry` は Python の関数を呼ぶ。別言語なら、その言語のプログラムを subprocess で呼び、
  結果の JSON を返す小さな Python 関数を `entry` にする

## ステップ4：健全性の確認

1. `python scripts/check.py` が通ること（サンプルを消した直後は、テストが0件でも通る）
2. **探索モードが動くことの確認**（数値の主張がある題材だけ）。本物の `runs/` を汚さないよう、キットを一時フォルダにコピーして行う
   （`sandbox/` の下にコピーする場合は、コピー元から `sandbox/` 自体を除く）。コピー先で：
   * `targets.json` の目標値を、届かない値に書き換える（コピー先だけ。本物は触らない）
   * 予測が外れる試行を、型を変えながら `stagnation_window` + 1 回より多く回し、`ledger.py` が「探索」と表示することを確かめる
   * 試した型の試行を `run.py` が拒否し（終了コード 3）、未試行の型の試行は通ることを確かめる
   * 確かめたらコピーを消す。結果（入ったか・拒否されたか）だけを報告に書く
3. `journal/decisions.md` に「K1: キットの組み替え」として、ステップ2の対応表・評価方法・仮説の型・数値の設定と根拠・変更点を記録する
4. ユーザーに次を伝えて終える：
   * 変更したファイルの一覧
   * 探索モードの確認の結果
   * （Claude Code の場合）`python scripts/adapt_mode.py off` を実行して保護を戻すこと
   * 開発の始め方：「`<名前>開発開始` と言ってください（題材のフォルダが無ければ作ります）」
   * 2段階の計画にした場合：第1段階の診断実験から始めること、目標値は結果を見てから人間が決めること
