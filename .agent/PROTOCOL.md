# PROTOCOL — 開発ループの手順

「<名前>開発開始」「開発再開」と言われたら、この手順に従う。
**どのフェーズでも、区切りごとに `.agent/progress.md` を更新する。** 途中で止まっても、次の起動（別のセッション・別のエージェント）がそこから再開できるようにするため。

```
フェーズ0 準備 → フェーズ1 主張の抽出 →【人間の承認】→ フェーズ2 計画
  → フェーズ3 内側のループ（実装） → フェーズ4 外側のループ（再現） → フェーズ5 締め
```

---

## フェーズ0：準備（毎回）

1. `lab.config.json`・`.agent/goal.md`・`.agent/guardrails.md`・`.agent/progress.md` を読む
2. 対象の題材 `<名前>` を決める
   * 「<名前>開発開始」なら、それが対象。`papers/<名前>/` が無ければ `python scripts/new_paper.py <名前>` を実行し、
     「`papers/<名前>/paper.md` に論文の Markdown を貼ってから、もう一度『<名前>開発開始』と言ってください」と伝えて**止まる**
   * 「開発再開」なら、progress.md の「現在の対象」と「現在のフェーズ」から続ける
3. `paper.md` が空（テンプレートのまま）なら、貼ってもらうよう伝えて止まる
4. `.agent/locks.json` に `<名前>` があるか確認する
   * 無い → フェーズ1へ
   * ある → フェーズ2へ（progress.md にタスクがあればフェーズ3へ）

## フェーズ1：主張の抽出（承認前）

1. `paper.md` を読み、**検証できる主張**を取り出して `papers/<名前>/claims.md` に書く
   * **性質の主張**：小さな入力で必ず成り立つこと（式の性質、不変性、境界での振る舞い）→ 単体テストにする
   * **数値の主張**：表やグラフの値 → 実験にする。目標値と許容誤差を `targets.json` に書く
   * 主張にならないもの（「優れている」「効率的」など測れない記述）は取り出さない
2. 性質の主張ごとに `tests/<名前>/claims/test_cN_*.py` を書く
   * テストは**論文の記述だけ**から書く。実装を見て合わせてはいけない（まだ実装が無いのが普通）
   * 実装が無いので、今は失敗してよい
3. 数値の主張ごとに、許容誤差の**提案**を理由付きで書く（乱数のぶれ、論文の有効桁など）。決めるのは人間
4. 論文に書かれていない点（初期値、定数、実験条件の抜け）を洗い出し、`journal/decisions.md` に「未確定」として列挙する
5. progress.md を「フェーズ1完了・承認待ち」に更新する
6. ユーザーに次の形で報告して**止まる**：

   > 主張を N 件取り出しました（性質 a 件、数値 b 件）。
   > `papers/<名前>/claims.md`・`targets.json`・`tests/<名前>/claims/` を確認してください。
   > 特に確認してほしいこと：（許容誤差の提案、判断に迷った主張、未確定の点）
   > 問題なければ `python scripts/lock.py <名前>` を実行してから「開発再開」と言ってください。

**`scripts/lock.py` は自分で実行しない。** 承認は人間の仕事。

## フェーズ2：計画

1. `python scripts/check.py` を実行する。ロック検査が通ることを確認する（テストの失敗は今はよい）
2. 主張ごとに `.agent/tasks/<名前>_CN.md` を `tasks/_TEMPLATE.md` から作る。順番は：
   * 性質の主張を先に（速く、決定的なので土台になる）
   * 数値の主張は、関係する性質の主張がすべて通ってから
3. progress.md の状態表に、全主張を「未検証」で並べる

## フェーズ3：内側のループ（実装）

対象のタスクを1つ選び、次を繰り返す。

1. `src/<名前>/` を実装・修正する
   * 数式そのものは `core/`（外部に依存しない。乱数は引数で受け取る）、組み合わせは `algorithm/`
   * 論文の記号とコードの名前の対応を `src/<名前>/README.md` の表に追記する。同じ記号に別の名前を付けない
   * 試しに動かしたいだけのコードは `sandbox/` に書く
2. `python scripts/check.py` を実行する
3. 失敗したら：
   * **直す前に**、失敗理由の要約を progress.md の「直近の失敗理由」に書く
   * エラーメッセージの指示に従って直す。**直すのは常に `src/` の側**（主張テストは編集できない）
   * 同じ失敗理由が3回続いたら、方針を変える。それでも駄目なら「ブロック」として止まって報告する
4. 成功したら、性質の主張は状態表で「検証済み」にする（証拠欄には `check` とテスト名）

## フェーズ4：外側のループ（再現）

数値の主張ごとに行う。**実行には時間とお金がかかるので、1周ごとに考えてから回す。**

外側のループには2つのモードがある。どちらにいるかは自分で決めず、`python scripts/ledger.py <名前> <主張ID>` の表示に従う。

* **通常モード**：`decisions.md` の「未確定」から、予測付きの仮説を1つずつ試す
* **探索モード**：直近の試行が目標にほとんど近づいていない（停滞）。前の周の微調整を続けても抜け出せないので、
  **まだ試していない型**か、**問題の性質を調べる診断実験**に切り替える。`run.py` もそれ以外は実行を拒否する

### 毎周の手順

1. `python scripts/ledger.py <名前> <主張ID>` で台帳を見る（モード・排除された型・未試行の型・予算）
   * 探索モードに入って最初の1回は、先に Reviewer を呼ぶ（`.agent/REVIEWER.md`）
2. `experiments/<名前>/cN_*.json` を書く（形式は `scripts/run.py` の先頭を参照）。`hypothesis` には次を書く
   * `text`：この設定で何を確かめるか
   * `type`：仮説の型（`lab.config.json` の `explore.hypothesis_types` のどれか）
   * `parent`：どの run の設定から1つ変えたか（資料どおりの設定なら `"root"`）
   * `prediction`：結果の数値の予測。**実行する前に**書く
   * `falsified_if`：予測が外れたら何を捨てるか
   * `based_on`（必要なときだけ）：根拠にした診断実験の run
3. 実験の前に、変更をコミットする（`run.py` が git のコミットを記録するため。git が無ければ省略）
4. `python scripts/run.py experiments/<名前>/cN_*.json`
   * 拒否されたら（終了コード 3）、表示された理由に従って実験 JSON を直す。拒否は記録に残らない
5. `python scripts/compare.py runs/<できたフォルダ>`
6. 判定ごとに：
   * **PASS** → 状態表を「検証済み」、証拠欄に run フォルダを書く
   * **判定不能** → 種のぶれで結論が出ない。params を変えずに seeds だけ増やし、型「統計的ばらつき」で回し直す。
     この結果から次の仮説を立てない
   * **FAIL** →
     * `journal/<今日の日付>.md` に「予測・結果・予測の当否・次の仮説」を書く
     * 予測が外れたら、`falsified_if` に書いたとおりにその仮説を捨てる。言い換えて同じ仮説を出し直さない
     * 新しい実験 JSON を作る（古いものは消さない。どの仮説で何が起きたかの記録になる）
     * 1 に戻る

### 診断実験（kind: diagnostic）

目標に当てにいくのではなく、「何を変えると結果がどう動くか」を調べる実験。停滞したときや、型が排除されたときに使う。

* `sweep` に、調べるパラメータ1つと値の一覧を書く（例：`{"param": "window", "values": [5, 10, 20, 40]}`）
* `parent` の run から、sweep するパラメータ以外は変えない
* `prediction` は要らない。結果は compare.py が値ごとの表で見せるので、分かったことを今日のノートに書く
* その run を次の試行の `based_on` に書くと、排除された型や探索モードでも、その情報に基づく試行が許される
  （**方向を変えるのは、新しい情報が入ったときだけ**）

### 打ち切り

`lab.config.json` の `budget` に達したら（`run.py` もそれ以上は実行しない）、Reviewer を呼んでから、
状態表を「再現不可」にし、試した仮説と結果を理由として書く。**再現不可は失敗ではなく、正式な終わり方の1つ。**

## フェーズ5：締め

次のどれかになったら締める。

* すべての主張が「検証済み」か「再現不可（理由付き）」になった
* 人間の判断が要る（ブロック）
* 予算が尽きた

やること：

1. `python scripts/check.py` が通ることを確認する
2. progress.md を最新にする（状態表・次の一手）
3. `journal/<今日の日付>.md` にこのセッションの要約を書く
4. ユーザーに**状態表をそのまま**報告する。「できました」だけで終えない

## いつ止まって人間に聞くか

* 承認（lock）が必要なとき
* ロックされたファイルを変えないと先に進めないと判断したとき（主張の誤り、目標値の誤記など）
* 論文の記述が矛盾していて、どちらを採るかで結果が大きく変わるとき
* 同じ失敗が方針を変えても続くとき
* 探索モードで、未試行の型も診断実験の予算も尽きたとき
* 仮説がどの型にも当てはまらないとき（型を足すのは人間の仕事）
* Reviewer の報告に「人間の判断が要ること」があるとき
* 予算に達したとき

止まるときは、progress.md の「次の一手」に「人間の判断待ち：〜」と書いてから報告する。
